# Changelog

## [0.48.3] - 2026-11-25

- On a Mac, a model that does not fit the memory free now is not started. The client reads the Mac's free memory the way vLLM Metal does (free, inactive and speculative pages from `vm_stat`), and refuses before vLLM starts, with both numbers, when the model's need (its weights plus one request at the configured context) is larger. The setup wizard checks this before it downloads. A Mac gets no memory share: vLLM Metal sizes its KV cache to the free memory itself. `flockadoo compatibility` now shows a Mac's free memory.
- When vLLM refuses to start because the memory left after loading the model cannot hold the KV cache for one request at the model's context, the client now explains it with vLLM's numbers, for example "one request at the model's 8,192-token context needs 0.88 GiB of KV cache, and only 0.53 GiB is left for it after loading the model", instead of "process exited". vLLM's advice to lower `max_model_len` is not passed on: a context below the catalog's fails verification.
- An orphaned vLLM engine process that macOS has paged out is reported as "memory paged out" instead of "0.0 GiB".
- On an NVIDIA GB10, the client no longer logs three "Failed to parse memory" warnings every 3 seconds: nvidia-smi reports a GB10's GPU memory as N/A, which means not reported, not a failure.

## [0.48.2] - 2026-11-25

- When the engine is not started (a model that does not fit the memory free, vLLM refusing for memory, or an engine that is not ready in time), the reason now stays on screen. It used to be printed once and cleared by the console half a second later, and it was not logged, so the machine showed a client with no engine and no reason. The reason is now logged, shown in a red Engine not ready row on the dashboard and the console, and given as `engine_not_ready` in `/api/status`. The row goes once the engine serves a model.

## [0.48.1] - 2026-11-25

- The out-of-memory messages no longer suggest a shorter context. A context below the catalog's `max_model_len` fails model verification, so that advice could not work. The "does not fit" message before the start and the explanation of a vLLM Metal "Insufficient Memory" refusal now end "Close other programs, or choose a smaller model" (the Metal one also names any orphaned vLLM engine process).

## [0.48.0] - 2026-11-25

- On a machine whose GPU shares its memory with the CPU (an NVIDIA GB10 / DGX Spark), vLLM now starts with a memory share that fits the memory free at that moment. vLLM reserves 0.92 of the total memory by default and refuses to start when that much is not free, which on a GB10 running a desktop happened even for a 2 GB model. Right before each start the client reads the free memory and passes `--gpu-memory-utilization` as min(0.92, (free − margin) / total), rounded down to 0.01, where the margin is 4 GiB or 5% of the total, whichever is larger (0.81 on a 128 GB GB10 with a desktop running). The share is not saved, so every start chooses again. A share you wrote into the engine command yourself is kept. Dedicated GPUs, Macs, llama.cpp and Team Flocks are unchanged. The share is logged and shown in a new Memory share row on the dashboard and the console, and as `memory_share` in `/api/status`.
- The concurrency benchmark records the memory share it was measured at. When the engine starts with a share more than 0.05 lower, the measured limit is scaled down by the same ratio straight away and the benchmark runs again; the Benchmark line says why.
- A model that does not fit the memory free now is not started. Before the engine starts (and before setup downloads the model), the client compares the model's need (its weights plus one request at the configured context) with the free memory: free VRAM on a dedicated GPU, free memory on a GB10, and on a GB10 the share vLLM will get. If it does not fit, it says so with both numbers, for example "needs about 14.80 GiB to start at a 32,768-token context; 10.00 GiB of GPU memory is free", instead of starting vLLM. When it cannot tell (a Mac, no GPU, several GPUs, a Team Flock, or the catalog cannot be read), it starts as before. When vLLM still refuses for memory, the client explains vLLM's refusal in plain words with vLLM's numbers, instead of "process exited: exit status 1".
- Before it starts an engine, the client reports vLLM engine processes (`VLLM::EngineCore`) of your user whose API server is gone. Such a process is left over from a vLLM that was killed and keeps holding memory. The client never stops it: it prints the process's pid, memory and age with the command to stop it (`kill <pid>`), logs it, and shows it in an Orphaned engines row on the dashboard and as `orphaned_engines` in `/api/status`. A vLLM that is running, however it was started, is not reported.
- An NVIDIA GPU that reports its memory as `[N/A]` (a GB10) is now treated as unified memory, like Apple Silicon: total and free memory come from the system. The compatibility check used to score such a machine as CPU-only or with unknown memory.

## [0.47.1] - 2026-11-25

- The engine now always starts on the commit the client serves and verifies. Setup saves the engine command once (`provider.engine_args`), with the commit approved at the time. When the client later moved to another commit (a newer one approved and downloaded), it saved the new `provider.hf_revision` but kept starting the engine from the old command. So the engine served the old commit while the client verified, and reported, the new one. At every start the client now sets the saved command to the configured commit: for vLLM, `--revision` and `--tokenizer-revision` on that commit and `HF_HUB_OFFLINE=1`; for llama.cpp, `-m` on that commit's cached file. A command saved before 0.46 (with no commit, or a llama.cpp command that fetches by repo and file) is pinned the same way. Other saved flags and variables stay. The config file is not rewritten. With no configured commit the saved command runs as saved.

## [0.47.0] - 2026-11-25

- `provider.hf_hub_cache` is removed. It only ever told the verifier where to look, not `hf` or the engine, so a machine that set it downloaded a model to one folder and was verified in another. A line left in `config.yaml` is ignored: at start (and in `flockadoo model`) the client warns that it is ignored, names the folder it uses, and the line is dropped the next time the client saves the config. Models are downloaded to, served from and verified in the Hugging Face cache (`HF_HUB_CACHE`, then `HF_HOME/hub`, then `~/.cache/huggingface/hub`). To use another folder, set `HF_HUB_CACHE` in the client's environment. `provider.model_path` still points the verifier at a flat folder of weights.

## [0.46.0] - 2026-11-25

- A model is now downloaded and served at the exact Hugging Face commit Flockadoo approved, so a change upstream can no longer change what a machine serves. vLLM starts with `--revision` and `--tokenizer-revision` set to that commit and with `HF_HUB_OFFLINE=1`, so it never downloads `main` by itself; llama.cpp is started with `-m` on that commit's cached file. Before the engine starts, the client picks the commit to serve: the one in the config while it is still approved, otherwise the current or the accepted one already on disk, otherwise it downloads the current one. It then saves the choice in the config as `provider.hf_revision` (with `hf_repo` and `gguf_file`). A commit that is no longer current, or that is retired, is reported at start and kept: a retired commit is not replaced automatically, because the download can be 20 to 60 GB. Against a server that lists no commits, the client serves the model as configured, as before.
- Model verification now measures the commit the engine serves and names it to Flockadoo (`hf_revision` in the verify call).
- New command `flockadoo model`: `download [alias] [--revision <commit>] [--skip-space-check]`, `list` (approved models on disk, with commit, status, size and the last verification result, without hashing anything), `verify [alias]` and `login`. Downloads use Hugging Face's own `hf` tool, from a private environment in `~/.venv-hf` that the client builds from pinned, hash-checked requirements. Before every download the client checks that the disk holding the cache has the model's size plus 10% free, and at least 2 GB spare. For a gated model, the client explains how to get access and runs `hf auth login` in your terminal. The token goes from you to Hugging Face's tool, and Flockadoo never reads, stores or sends it.
- The setup wizard now pins the commit, downloads it, and only then starts the engine.
- Every machine in a Team Flock now serves the same commit, the one Flockadoo names: the master's while it is still approved. Each machine downloads that commit before the client shows the engine command.
- The Hugging Face cache is found the way Hugging Face finds it (`HF_HUB_CACHE`, then `HF_HOME/hub`, then `~/.cache/huggingface/hub`, which `XDG_CACHE_HOME` moves), and the client logs the folder at start. `provider.hf_hub_cache` in `config.yaml` is deprecated: it only told the verifier where to look, not `hf` or the engine. The client now warns when it is set. Set `HF_HUB_CACHE` instead; the option goes away in the next release.
- `uv` is no longer installed with `curl … | bash`. The client downloads a fixed `uv` release (0.13.9) and checks it against a SHA-256 built into the client before unpacking it into `~/.local/bin`. This also works on Windows. A `uv` already installed is used as it is.
- The llama.cpp release archives are checked against a SHA-256 built into the client before they are unpacked. On Windows both archives are checked before either is unpacked, so a bad download leaves nothing half installed. On a Mac, the archive's library symlinks (`libllama.0.dylib` and the like) used to be unpacked as empty files. They are now created as links, and only to files in the same folder.

## [0.45.1] - 2026-11-23

- A machine stays available while Flockadoo restarts. During a restart Flockadoo answers the model verification call with "404 page not found", and the client took that as "not verified", so Flockadoo recorded the model as failed and the machine as unavailable until the next check, up to ten minutes later. A 404, 408 or 429 now counts as Flockadoo being unreachable, like any outage: the last "verified" answer is kept for up to 30 minutes and the client asks again. A model not yet verified waits for its first answer instead of being reported as failed. A rejected API key or client version still refuses at once.
- The browser dashboard now shows the same rows as the console, in the same order, including Platform connection (it used to show a Connection row only when there was an error). The Benchmark and Capabilities rows always appear: when the benchmark is skipped, the line gives the limit in use ("fixed limit of 1" on llama.cpp, or "limit of N set in config"), and an embedding model's Capabilities line reads "verified for embedding". `/api/status` gains `platform_connection` and `platform_connection_failed`.

## [0.45.0] - 2026-11-23

- The client is now built with Go 1.27 (it was Go 1.23, which no longer gets security fixes). On a Mac it needs macOS 13 Ventura or later; Go 1.27 does not run on macOS 12 or older. Linux and Windows requirements do not change. Go 1.27's newer defaults also apply: TLS 1.2 no longer accepts SHA-1 signatures, TLS offers more post-quantum key exchanges, and in a container the client uses only as many threads as the container's CPU limit allows.

## [0.44.1] - 2026-11-20

- After a restart, the first health report waits (up to a minute) for the model's verification answer that is already being fetched. It used to go out without one, so Flockadoo recorded the model as failed and the machine as unavailable until the next report, three minutes later. A report for a model that already has an answer never waits.
- Hashing the weight files no longer holds up requests or health reports. It used to run under the verifier's lock, so while a large `.bin` was hashed (about 20 seconds for a 2 GB file) every request waited for it.

## [0.44.0] - 2026-11-20

- Inferoute is now Flockadoo, Inferscale is now Winglink, and a provider's cluster is now a flock: a Solo Flock is one machine, a Team Flock is a master and its workers. The binary is `flockadoo` (`flockadoo setup`, `flockadoo update`); the config is `~/.config/flockadoo/config.yaml`, where `provider.cluster_mode` is now `provider.flock_role`; the dashboard and the console say FLOCK STATUS, Platform URL and Engine. The client talks to `core.flockadoo.ai`, with the `X-Flockadoo-*` headers and a `flockadoo/<version>` User-Agent, and joins a Team Flock over Winglink (`winglink`, `winglinkd`, interface `winglink0`). Nothing keeps the old names: a machine on the old client is reinstalled.
- Winglink, the network a flock runs on, is now installed from one pinned release, and every file is checked against the SHA-256 built into this client before it is installed or run. A download that does not match is deleted and joining a flock stops with an error; an installed binary that does not match the pin is replaced. `WINGLINK_VERSION` no longer changes which release is used. Until this build pins a release, joining a flock stops with "update the client".
- A model stays served through a short Flockadoo outage. Verification is refreshed in the background every 10 minutes; when Flockadoo cannot be asked, the last "verified" answer is used for up to 30 minutes more, after which requests get 503 ("temporarily unavailable"), never 403. A "not verified" answer still refuses at once, and new or changed weights are never served on an old answer. An outage is no longer reported to Flockadoo as a failed verification, and serving a request no longer waits on a verification call.
- Stopping the client (Ctrl+C, `docker stop`, a service stop) now lets the requests it is serving finish, for up to 60 seconds, after telling Flockadoo it takes no more; a second Ctrl+C stops at once. The Docker examples give the container 75 seconds to stop.
- When the engine stops answering, the client tells Flockadoo it is not accepting requests within about ten seconds, and accepts again as soon as the engine answers; the dashboard says "engine down". The client does not restart the engine. The client also reports not accepting while its connection to Flockadoo is down.
- A client whose API key is rejected, or that Flockadoo asks to update, now stays running and shows why on the dashboard and the console, and stops reporting to Flockadoo, instead of exiting at startup or silently going quiet later. It does the same when Flockadoo says another client has taken over the key. When the connection keeps ending within a minute, the dashboard says another client may be using the same API key.
- A connection to Flockadoo that stops answering without closing is noticed within about 25 seconds and reopened.
- When the engine's answer breaks off partway, the client now aborts the stream to Flockadoo instead of ending it cleanly, so a cut-off answer can never pass for a complete one. Each request on the dashboard shows how it ended (completed, refused_busy, engine_failed, stalled and so on), and only completed requests count as successes.
- An engine that stops sending for three minutes during a streamed answer, including before its first word, is cut off and its slot freed, instead of holding the slot until Flockadoo gave up. A non-streaming answer sends nothing until it is finished, so this limit does not apply to it; the engine timeout (`llm_timeout_seconds`, at least 330 seconds) and Flockadoo's own limit still bound it.
- A request body larger than 16 MiB is refused before it reaches the engine. Streaming is read from the request's own `stream` field, not by searching the body.
- `max_concurrent_inference` must be 1 or more. `0` (which meant unlimited) or a negative value now stops the client at startup with a message saying what to set. Leaving it out still lets the client measure the limit.
- Returning turns of a conversation that wait for a free slot are now served in the order they arrived, and as soon as a slot frees (they used to check every 100 ms and the quickest won). At most 32 wait at once (`server.session_queue_limit`); a turn beyond that is refused at once so Flockadoo can send it elsewhere. When the concurrency benchmark starts, waiting turns are refused at once rather than waiting it out.
- The local web server (`127.0.0.1:8080` by default) no longer answers `/v1/chat/completions`, `/v1/completions` or `/v1/embeddings`. Inference from Flockadoo arrives on the client's own connection to Flockadoo, as before; to use your model yourself, talk to your engine directly. The dashboard, `/api/status`, `/api/health` and `/api/busy` are unchanged.
- The client no longer asks Flockadoo to confirm each request (the `validate_hmac` call). A request that arrives on the connection the client opened with its key comes from Flockadoo; requests are now served even while Flockadoo's API is briefly unreachable, and each one is answered without that round trip.
- The deployment fingerprint reads the engine's version from the running engine instead of running `<engine> --version` once a minute. An engine upgrade now counts as a new deployment, so the concurrency benchmark and the capability checks run again. The fingerprint changes once after this update, which re-runs them once.
- An engine `/metrics` value that is out of range, NaN or infinite (a KV cache usage above 100%, a negative queue) is now left out of the capacity report instead of being sent. A NaN used to make the whole report fail, so it was never sent.
- A stream time limit from Flockadoo larger than 24 hours is capped at 24 hours. A very large value used to overflow and end every write to that stream at once.
- A model file whose safetensors header claims an impossible size (more than the format's 100 MB limit) is now refused with an error during verification. It used to crash the client.
- `provider_type` is no longer a setting in `config.yaml`: `engine` is the one setting, and the provider type sent to Flockadoo (vllm, or llama_cpp) is worked out from it, as before. A `provider_type` line left in an older file is ignored, which is what already happened in effect, and `setup` no longer writes one.
- A platform address of `http://localhost:80` in `config.yaml` is now used as written. It used to be replaced with the production address; a file that still holds it will not connect until `url` is corrected or `setup` is run again.
- The Docker image no longer contains `cloudflared`, which nothing used.
- Reconnecting to Flockadoo is fast again after a long run. The wait before a reconnect used to double on every disconnect and never come back down, so a client that had dropped six times waited 32 to 48 seconds before every reconnect for the rest of its life. It now starts again from one second after a connection that lasted a minute. A connection that drops sooner still backs off, so two clients started with the same key do not knock each other off at full speed.
- A reasoning model (one that thinks before it answers, such as Qwen3, DeepSeek-R1 or gpt-oss) is started with the reasoning parser its approved-catalog entry names (`--reasoning-parser` on vLLM and vLLM Metal), so its thinking is sent apart from its answer. On llama.cpp the entry turns on `--jinja`, which does the same. The parser is saved in `config.yaml` as `reasoning_parser`; an existing install picks it up when `setup` is run again.
- A reasoning model gets a sixth capability check: the client asks it to think and reports whether the thinking comes back apart from the answer. The inference node serves a reasoning model only from providers that pass. Other models skip the check. Turning a tool or reasoning parser on now counts as a new deployment, so the checks run again.
- The health report includes the engine (vLLM, vLLM Metal or llama.cpp) and its version, read from the running engine (`/version` on vLLM, `/props` on llama.cpp), so the dashboard shows them on Solo Flocks. The local `/api/health` snapshot shows them too.

## [0.43.0] - 2026-11-12

- Installing without the wizard (`INFEROUTE_SKIP_SETUP=1`, and Docker) now needs `PROVIDER_MODEL` and runs `setup`, which checks the model against the approved catalog. `setup` gains `--llm-url` and `--port`.

## [0.42.0] - 2026-11-11

First release.

- Reports GPU temperature and power draw on NVIDIA and Apple Silicon, and GPU memory and utilization on macOS.
- macOS binaries are built natively.
- Errors go to `error.log` instead of the terminal and dashboard.
- Runs vLLM, vLLM Metal, or llama.cpp.
